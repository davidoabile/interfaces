# Sigmar AOS settings review

**Sigmar AOS settings review — 26 November 2026, Australia/Melbourne**

**Recommendation: replace the sparse preference canvas with eight compact settings sections, led by understandable AI access, account scope and data controls.** The present screen establishes visual consistency but does not explain who can access a Persona, what a permission change affects, whether changes have synced, or how account security works. The old Flutter app supplies useful source evidence, especially for registered AI clients and Persona grants; most of its general-setting switches do not persist. Its investment-era labels should not become the new AOS specification. Current governance supersedes the single-Flutter-client architecture, while the approved product direction requires a chat-first, Persona-based experience with separate Guild governance and Flow approvals. The next deliverable should be one substantive macOS Settings sample, followed by explicit review before extending this redesigned direction. This report proposes that sample and its implementation priorities; it does not change mockups, requirements, permissions or approvals.

### AI permissions are the strongest substantive starting point

The member AI settings read model defaults to **read off, write off, public-key requirement on, signed requests on, Persona allowlist on and auto-commit off**. Updates enqueue a `MEMBER_AI_SETTINGS` command; the domain models an auditable event-sourced member master gate. These are observed source defaults, not newly approved product choices. Turning a gate on does not bypass the client grant, Persona allowlist, role or action authorization. With auto-commit off, proposed writes route through a Flow. ([AI read model](</Users/doabile/workspace/hedgetech-wt-native-sync/sigmar-investment-app/lib/src/core/sync/ai_settings.dart:3>), [outbox update](</Users/doabile/workspace/hedgetech-wt-native-sync/sigmar-investment-app/lib/src/core/sync/sync_service.dart:2356>), [member domain](</Users/doabile/workspace/hedgetech-wt-native-sync/crates/htql-domain/src/member_ai_settings.rs:5>))

The customer-facing list should show client identity, selected Personas/data scope, permitted action, status and Suspend/Revoke actions. Proposed-write copy should say “Can propose changes” rather than “Can change everything.” Cryptographic requirements and allowlist enforcement belong in protected policy/advanced review, with reasons for any lock. **Do not add a casual “Allow AI changes” or “Run everything automatically” switch.** Effective access is the intersection of member policy, client status, scoped grant, Persona authorization and the specific action's requirements. A local optimistic update must appear as Pending until accepted, with a recoverable rejected state rather than a false success message.

### Native placement should reduce confusion

On macOS, use a dedicated Settings window reached from the app menu with **⌘,**, also reachable from the profile menu. Use stable category navigation, a clear active pane and remembered last pane, consistent with Apple's settings guidance. The Tauri window/menu integration is an implementation dependency. On web, use an accessible page or panel with stable category links and an obvious return to the conversation; deep links depend on routing support. On iOS/Android, use a scrollable category list and detail screens with native back navigation. The primary phone app menu remains a side drawer. ([Apple HIG: Settings](https://developer.apple.com/design/human-interface-guidelines/settings), [project responsive requirements](</Users/doabile/Documents/ChatGPT/Interfaces designs/MOCKUP_REQUIREMENTS.md:438>))

**A dedicated Settings window needs no chat composer.** The approved microphone rule applies whenever a conversation composer appears; it does not require putting a decorative composer on a settings utility window. If settings remains embedded in the chat workspace, any retained composer must still show typing, attachments and Talk to Sigmar. Search should find control names and synonyms such as mic, voice, privacy and PIN, take the user to the owning pane, and identify contextual destinations rather than duplicate them. Search is a proposed feature. Do not index private conversation content into settings search.

Display “This device”, “Your member account”, the active personal/business account, or the named Persona on the affected group. Search results must retain that scope. A locked setting should explain who manages it and provide an authorized review/contact route where one exists. Switching account should refresh account-scoped panes and prevent editing stale account details; switching must not silently widen member permissions. Personal device appearance must not unexpectedly become organization policy.

### Accessibility should work before any preference is changed

Keyboard reachability, meaningful names/roles/states, visible and unobscured focus, sufficient contrast, text resizing, reflow and reduced motion are engineering requirements across these panes. The project requires 44-point Apple and 48-dp Android targets. WCAG 2.2 provides relevant web criteria, including keyboard access, 200% text resize and 24-CSS-pixel minimum targets with exceptions; that web minimum does not reduce the project's larger touch targets. Use real error text and enlarged content during verification. A mockup cannot establish conformance, and this report makes no compliance claim. ([WCAG 2.2](https://www.w3.org/TR/WCAG22/), [project native/accessibility requirements](</Users/doabile/Documents/ChatGPT/Interfaces designs/MOCKUP_REQUIREMENTS.md:438>))

Guild DNA modification follows proposal, vote and application with separated proposer/voter/applier responsibilities. A personal settings switch cannot replace this. The provider architecture resolves provider configuration at compilation into immutable CompiledDNA and requires recompilation for behavior-affecting changes; it does not establish a live universal model dropdown. Avoid API-key forms, automatic provider failover, local-only processing claims or publisher-controlled model changes until implementation, external processing and licence boundaries are verified. Registered client public keys are not provider API secrets. ### Three permissions must never masquerade as one

**Signed AI authority** governs whether a registered client can read or propose changes over specifically granted Personas under member/domain policy. **OS/browser microphone authorization** governs whether this installation/site can capture audio. **Optional model-training use**, if offered, governs a separate data use; it does not authorize source access or recording. Enabling any one cannot be described as enabling the others. Persona learning into experience/compiled DNA is also distinct from a provider using conversations to improve a general model. The Sigmar guide expressly says permission to view is not automatic permission to learn. ([Limited view and learning](</Users/doabile/workspace/hedgetech-wt-native-sync/workers/sigmar-aos-site/app/ai/security.md:84>))

Show microphone states such as Not requested, Allowed and Blocked only when the platform adapter can determine them; otherwise show an honest unavailable status and guidance. Ask when the user initiates speaking. Preserve typing after denial. A voluntary management link or instructions must not imply the app can flip OS permission, and must not pressure the user by automatically opening settings after denial. Browser grants can be one-time or removed later, so remembered account preference is not permission proof. No cross-platform deep-link scheme was verified. ([Android runtime permissions](https://developer.android.com/training/permissions/requesting), [Chrome site permissions](https://support.google.com/chrome/answer/114662?hl=en))

Voice settings must distinguish dictation/capture, transcript review, full spoken conversation, synthesized playback and audio retention. The approved microphone icon is not proof of background listening, live voice or retained audio. A benchmark voice product documents explicit stopping and separate transcript behavior, useful distinctions rather than evidence of Sigmar support. ([Claude voice guidance](https://support.claude.com/en/articles/11101966-use-voice-mode))

### Data controls need named objects and honest consequences

| Data object | What a control must specify | What it must not imply |
|---|---|---|
| Conversation history/transcripts | Which conversations, account, retention and derived-context relationship | Deleting a chat automatically deletes memories, knowledge, trained models or all remote copies. |
| Saved personal context / Persona experience | What has been saved, which Persona uses it, review/correction and removal boundaries | Pausing future personalization erases prior derived information. |
| Knowledge/source material | Ownership, connection versus copied/imported content, selected scope and learning permission | Disconnecting a source automatically deletes previously imported/derived data. |
| Training inputs and learning eligibility | Which use, recipient/model, consent, future-use effect and existing artifacts | Read permission is training permission; opting out reverses completed training. |
| CompiledDNA / licensed or published artifacts | Artifact/version, source separation, licence and governance dependencies | A global history reset recalls licensed artifacts or trades source DNA. |
| Local replica, downloads and unsent writes | Device-only removal versus synchronized data; pending work and recovery prerequisites | Reinstalling, resetting sync or clearing cache is always harmless. |

Only compiled DNA is described as shared/leased/sold; source is not traded. The sync design distinguishes a valid local replica and applied checkpoint from server cursor state, requires preservation of unsent offline writes across rebootstrap, and identifies unrecoverable risk when local-only writes are absent. Accordingly, a storage screen needs pending-write visibility before cleanup/reset; there is no basis here for a reassuring “Everything is safely synced” message. Exact retention/export/deletion contracts remain unresolved. ([Source versus compiled DNA](</Users/doabile/workspace/hedgetech-wt-native-sync/htql/docs/website/sigmar-about-page.md:173>), [sync contract](</Users/doabile/workspace/hedgetech-wt-native-sync/htql/docs/user-data-sync.md:49>), [pending writes/rebootstrap](</Users/doabile/workspace/hedgetech-wt-native-sync/htql/docs/user-data-sync.md:88>))

For a future irreversible action, the confirmation design should name the object, scope, pending work, what remains and whether it can be undone. “Revoke this client's future access to these Personas” must not promise to undo previous external actions. “Remove this business account” must explain retained records rather than claim erasure. Export, erase-history and delete-account confirmations require supported authorization and lifecycle contracts before they appear as available actions. These are design requirements only; no action is executed by this report.

Official assistant benchmarks reinforce separation rather than feature parity. Claude documents distinct history, memory and project-memory behavior; its current and legacy memory sections differ on deletion effects. Its retention and model-improvement guidance separately describes processing and training choices. None supplies a Sigmar retention duration or deletion guarantee. Its connector guidance separates connecting a service, contextual enablement and underlying source permissions; that supports clear scope labels but does not prove Sigmar OAuth support. ([Claude memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context), [Anthropic retention](https://privacy.claude.com/en/articles/10023548-how-long-do-you-store-my-data), [Claude connectors](https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities))

### Preserve passwordless sign-in and verify recovery

The accepted login uses email/mobile and a six-digit one-time passcode; AOS locking uses a five-digit PIN. Requirements explicitly prohibit inventing passwords/social login/biometric alternatives and require the maintained recovery specification before designing PIN recovery. Android's current PIN screen calls core unlock, which supports a real lock concept but does not prove change-PIN, biometric unlock, session revocation or recovery settings. Offer verified operations and accurate help, not a polished list of unsupported security promises. ([Authentication requirements](</Users/doabile/Documents/ChatGPT/Interfaces designs/MOCKUP_REQUIREMENTS.md:191>), [Android PIN unlock](</Users/doabile/workspace/hedgetech-wt-native-sync/clients/android/app/src/main/kotlin/io/sigmar/nativeapp/PinLockScreen.kt:23>))

### Notification preference does not guarantee delivery

Subscription state answers “Which events do I want?”; device permission answers “Can this installation deliver them?”; Android channel settings and Apple Focus further affect interruption. Android 13+ notification permission and Android 8+ channels remain authoritative; the app cannot silently raise an existing channel's importance. Do not claim essential security or approval events bypass denial, Focus or channel choices. If quiet hours/digests are later implemented, specify account/time zone, delayed categories and handling of expiring approvals; do not silently delay urgent decisions. ([Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission), [Android channels](https://developer.android.com/develop/ui/compose/notifications/channels), [Apple Focus](https://support.apple.com/en-gb/guide/mac-help/mchl613dc43f/27/mac/27))

Interface language should follow system behavior, with a picker only for translated resources. Android's per-app language APIs should keep its in-app/system setting consistent; this is not cross-device member synchronization. Speech-recognition and response-language preferences require separate support. ([Android per-app language](https://developer.android.com/guide/topics/resources/app-languages))
